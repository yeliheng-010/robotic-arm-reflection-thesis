**原始请求确已追加拒绝反馈，模型仍输出同一动作，输出后的重复门禁正确拦截。可以确认存在上一阶段指令残留；导致模型重复的具体原因尚未建立。** 草案不是修复验证结果。

## 确认的事实与排除范围

1. 两份请求只有用户正文的 `history` 和 `budget` 改变：历史从4条增加至5条，决策/规划剩余预算2→1。图像、系统指令、完整观测、动作范围、目标箱几何与任务定位信息一致。新增历史为 `long_positive/20/0/0/0` 的 `rejected/grasp_endpoint`，没有私有接触实体、坐标或推荐姿态。
2. 两份原始响应的44个生成 token 和动作完全相同，严格 JSON 解析后的动作与原文相同。记录输入长度10552/10606，输出均 EOS 结束。源码在超过16384时拒绝，不采用输入截断；已保存长度在上限内。此处支持原始请求构造及记录长度正确，不等于重建了历史完整输入张量。
3. 系统原本已经包含“自主选一个不同的抓姿或STOP”“禁止重复被拒绝的动作”。并非缺少禁止重复指令。`validate_response` 只检查格式与白名单；[permitted](../qualified_feedback_v1/policy.py) 在生成之后、规划之前检查历史重复。第二次没有新增 private_plan，旧安全门禁按设计生效；这并不保证生成器一定遵守提示词。
4. 生成入口每次创建新的 VisualGenerator；`do_sample=False`、seed=42、`enable_thinking=False`。`use_cache=True` 是单次生成的 KV 缓存，所读路径没有按旧请求返回旧响应的逻辑。固定种子/贪心解码不要求不同输入产生不同答案，也不足以解释本次重复。记录生成耗时分别约6.597/6.543秒；不能据相同输出认定未真实生成。
5. 本次白名单包含738种满足 `tilt=0 => azimuth=0` 的抓姿参数组合，历史只拒绝其中5种，另允许 `STOP`。未发生白名单穷尽；未尝试的组合安全性未知，不能把733个未拒绝组合当作733个可行抓姿。

第一决策在8个抓取端点全部被拒绝，第二决策在重复门禁停止。两者均未进入新闭合门禁，不能据此认定闭合预检过于保守，亦不能推断完整任务成功率或模型普遍的反思能力。

## 可修改问题与尚待验证的假设

**已确认的阶段指令残留：** `task_grounding.task` 仍是“任务：把紫色胶囊放进橙色箱子。请定位待抓物体和目标容器。”末句来自定位阶段，而当前要求选择抓姿动作。清理有助于语义一致，但模型实际仍按动作 JSON 输出，不能把该残留写成已证明的重复根因。

**反馈显著性是假设：** 第二次正文12102个字符，128目标点和256邻域点序列共9867字符，约占81.5%。历史从字符偏移10640开始，长度934字符，之后还有输出限制、目标箱几何和任务定位信息。这是字符统计而非 token 统计；反馈已经靠近末尾，不能直接称为“丢在上下文中间”。在末尾明确提醒比较完整历史，是值得单独检验的改动，不是已知有效方案。也没有受控证据把问题归因于上下文长度或4B模型规模。
