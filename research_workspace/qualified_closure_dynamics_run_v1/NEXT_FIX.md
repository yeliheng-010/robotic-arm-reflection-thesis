# 下一版修复建议：区分项目代码与嵌套虚拟环境依赖

当前仅建议，未修改qualified_closure_dynamics_v1冻结入口，未追加轨迹预算。

已确认：entry.py的imported_sources使用resolved_path.is_relative_to(PROJECT)确定项目源码。实际sysconfig的purelib/platlib均在PROJECT/env_sim/lib/python3.11/site-packages下，因此setuptools的_distutils_hack被纳入项目来源校验，但原1332项准备清单没有这项依赖文件，导致场景创建前中止。

这不是已发现的碰撞、MuJoCo数值问题或抓姿失败，也不是已证实的依赖篡改。独立审计只确认当前依赖文件匹配setuptools 79.0.1的安装RECORD；原准备清单没有其历史哈希，因此不能追溯宣称该依赖在旧准备/执行期间始终未变。

建议在独立新版本处理：

1. 用解析后的路径和当前解释器的sysconfig/site信息明确项目源码、第三方包、标准库边界；不要只按项目目录前缀或路径中含site-packages字样排除。
2. 第三方依赖仍须登记真实导入文件哈希、解释器/包版本、安装记录及对应解析路径；不能直接跳过依赖来源验证。
3. 在不创建场景、不调用积分的受保护预检中加载实际运行导入集合并绑定来源，验证通过后再登记新的执行claim，防止将导入分类错误留到消耗轨迹预算之后。
4. 回归覆盖嵌套虚拟环境、项目自己的同名目录、路径穿越/符号链接解析、缺失或变化的项目文件、真实依赖文件变化、虚拟模块__file__、缺授权和重复claim。测试仍通过Slurm，禁止场景创建和mj_step系列调用。
5. 先完成该修复和零积分真实导入验证；本次claim保持consumed=1，不迁移、不清空、不复用。之后若继续动力学诊断，另行明确有限预算并保留本轮失败记录。

验收以来源分类正确且来源完整绑定为准，不以“忽略这个包后程序不报错”为准。
