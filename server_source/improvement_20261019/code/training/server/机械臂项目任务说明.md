## 无头运行的机械臂操作

无头模式仍调用 `UR5GraspEnv` 和 `GraspFlow`，机械臂抓取、搬运、释放都在 MuJoCo 物理仿真执行；只是不弹窗口。`simulation` 感知提供仿真目标位置和掩码，便于隔离反思机制；它不能作为完整 VLM 视觉性能结果。

服务器上运行单条自然语言指令：

```bash
cd /home/yeliheng/VLM_Grasp_Interactive
srun --partition=batch --gres=gpu:v100:1 --ntasks=1 --cpus-per-task=8 --mem=24G \
 env MUJOCO_GL=egl MPLCONFIGDIR=/tmp/grasp-mpl OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 \
 /home/yeliheng/grasp_server/env_sim/bin/python -m reflection \
 --headless --task-parser rule --reflector rule --method reflection \
 --perception simulation --segmentation simulation --grasp-backend geometric \
 --fault collision --instruction '把红色方块放进蓝色箱子' \
 --output /home/yeliheng/grasp_server/manual_collision
```

`--instruction` 指定任务；也可用 `--source RedBlock --destination BlueBin`。源物体包括 `RedBlock GreenCylinder PurpleCapsule OrangeSphere`，目标包括 `BlueBin RedBin SortingTray`。suite 包装器仅支持前两个源物体。不要手动覆盖 Slurm 设置的 `CUDA_VISIBLE_DEVICES`；分配到物理 GPU 2 的进程通常看到的是 `cuda:0`。必须显式写 `--ntasks=1`，避免继承默认值启动两份。

正式视觉链路是 `--perception vlm --segmentation sam --reflector llm`，按需 `--visual-verify`。它还需要可用的多模态推理端点和凭据，文本教师端口 18765 不提供这些接口。当前教师修正实验没有冒充完整视觉实验。

## 一键采集与恢复

第一批组合：2 个物体 × 3 个容器 × 5 类故障 × 2 个种子 = 60 项任务，每项最多 3 次尝试，场景位置抖动上限 12mm。故障为 planning、grounding、calibration、collision、placement。首批用于检查数据产出、覆盖和失败原因，不是正式论文测试集。

首批已提交时不要重复运行。以后启动新批次：

```bash
cd /home/yeliheng/VLM_Grasp_Interactive
bash training/server/run_pilot.sh /home/yeliheng/grasp_server/collections/pilot_v2 2 2000
```

脚本提交一个冻结教师作业、一个物理验收作业和一个采集作业；两张 GPU 轮流执行验收/采集与教师推理。采集包装脚本检查本批物理验收结果，再等待教师健康检查（最多240秒）；验收失败或采集退出会清理本次教师。教师端点仅监听服务器 `127.0.0.1:18765`，不调用付费 API、不载入单样本过拟合 adapter。正式采集不使用响应缓存。中断后保留结果：重新启动教师，并对**同一个输出目录、相同参数和相同代码**提交 `collect.slurm` 即恢复已完成任务。记录新教师作业号，在提交时传入自动清理变量。

```bash
cd /home/yeliheng/VLM_Grasp_Interactive
# 先确认端口没有已有教师；以下 TEACHER_JOB 由 Slurm 返回，不是固定数字。
TEACHER_JOB=$(sbatch --parsable training/server/teacher.slurm)
sbatch --export="ALL,GRASP_TEACHER_JOB=$TEACHER_JOB" training/server/collect.slurm \
 --output /home/yeliheng/grasp_server/collections/pilot_v1 --seeds 2 --start-seed 1000
```

采集程序检查配置、代码指纹和教师身份；发生变更应换新输出目录，不能手改 manifest 绕过检查。教师加载需要时间，启动采集前确认 `curl -sS http://127.0.0.1:18765/health` 返回当前模型信息。`ready.json` 是历史启动记录，不能代替活性检查。

结果：

- `manifest.json`：模型、提示格式、冻结身份、配置、代码指纹。
- `plan.json`：所有任务的物体、容器、故障和种子。
- `tasks/00000/result.json`：逐次物理验收、错误证据、修正及实执行参数。
- `tasks/00000/attempt_N/`：执行前后图片、掩码与计划。
- `verified_train.jsonl`：去重后、LLM 修正紧接一次物理成功的样本池。
- `status.json`：已完成任务、成功任务、有效修正数、无效输出数及故障覆盖。
- `~/grasp_server/teacher/requests.jsonl`：教师原始输入输出，模型身份和耗时。

有效样本要求：修正来源确实是 LLM；参数合法；下一次实际采用该参数；下一次同时 `accepted=true` 和 `physical_success=true`。规则数据不进入 LLM 样本。故障注入标签、未来成功标签和图片私有路径不作为文本输入。直接成功的任务是评估记录，不是反思修正样本。

注意：当前 planning/grounding 注入仅发生在第一次尝试，下一次会自然消失。修正后成功只能作为候选样本筛选证据，不能证明是该修正带来的恢复收益；这两类必须与同预算 retry 配对比较。calibration/collision/placement 则为持续故障。正式数据集和论文结果必须保留这个区别。

## 模型与训练路线

“Qwen3.5”是模型系列名称。官方已核对 `Qwen/Qwen3.5-4B` 与 `Qwen/Qwen3.5-9B`；本次优先验证 4B，没有擅自称其为 3.5B 参数模型。

已完成的旧测试：Qwen2.5-7B 在单卡 V100，NF4/FP16、rank8、梯度检查点，8 个优化步骤；峰值 PyTorch 分配约 9.26GiB，adapter 保存重载一致。仅 1 条样本，实际 326 token。这只证明运行流程，不证明机械臂效果。

Qwen3.5 使用不同的混合注意力架构。专用环境为 torch2.6.0+cu124、transformers5.20.1、PEFT0.21.2、bitsandbytes0.49.2。V100 使用 FP16，禁用 BF16/FlashAttention2；先测 eager/PyTorch 回退。`qwen35_env.sh` 设置共享 CUDA 库搜索路径，不修改旧环境。专用 smoke 只训练语言层 LoRA，冻结视觉部分，但输入是文本，不等于完成多模态微调。

```bash
cd /home/yeliheng/VLM_Grasp_Interactive
# 数值稳定性重试：小 AMP scale，保持 delta-rule 参考运算为 FP32。
# 当前3614已经排队，不要重复提交。以下供之后检查使用。
sbatch training/server/qwen35_retry.slurm
```

每个作业保存到 `~/grasp_server/qwen35/runs/smoke_作业号/`，检查 `smoke_result.json` 中的状态、有限梯度、实际更新、保存重载误差。新模型检查未通过前不能把 7B 的结果套用过来。不能把单卡 1024 上限当成实际测试长度。

重试代码位于 `~/grasp_server/qwen35/debug/{smoke_train.py,data.py}`，保持采集时项目 Python 代码指纹不变。原 `qwen35_smoke.slurm` 保留首次配置供追溯；重试使用独立快照，结果决定是否正式采用该配置。它仍只有1条旧样本、8步，仅检查兼容性，不是正式训练或效果提升。

扩大路线：先分析 60 项试采质量与恢复率，再扩充错误阶段、视角、位置、干扰、对象和指令。可按 1000～3000 条独立且经过验证的修正作为早期目标，但是否足够取决于学习曲线、覆盖和独立测试，不靠重复种子凑数。按场景/任务族/种子组切 train/validation/test，同一轨迹、近重复场景及其所有重试必须同组；先冻结测试再筛选训练样本。基线/重试/规则反思/原模型/微调模型使用配对任务、固定预算和无响应缓存。报告物理成功、故障恢复、无效 JSON、调用量、耗时和显存。

目前没有四卡 DDP/FSDP 的实测结果。四卡释放后优先考虑1卡教师、2卡独立采集、1卡训练/评估；实际分配需按调度资源和模型显存核对。多 worker 不能写同一个 run、sqlite 或文件。需要多卡训练时先实现并测梯度一致性、显存和实际速度，再决定使用 4B/9B；不要简单 `device_map=auto` 就声称多卡训练完成。
