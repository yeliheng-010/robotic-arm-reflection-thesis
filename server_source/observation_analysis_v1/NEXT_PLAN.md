# 同预算观测处理与模型选择对照实施方案

状态更新：observation_model_control_v1的24条件96方法轨迹已全部完成，最终审计5278通过，服务5268正常退出。相同聚合方式下规则与基础4B逐条件成功结果一致；两者预算3均latest22/24、median24/24。详细结果见该目录RESULTS.md与verification.json。本文件以下保留原设计与验收目标。

## 研究问题和四组设计

在既有24开发条件上，分别检验观测聚合与动作选择器。全部保留，包括5个初始成功、无离群、无收益和两次离群条件，不只跑3个改善案例。

| 方法 | 有效反馈 | 选择器 | 被比较的作用 |
|---|---|---|---|
| rule_latest | 同状态三次测量中的最后一次 | 既有规则 | 规则基线 |
| rule_median | 同状态三次测量的逐坐标中位数 | 同一规则 | 与rule_latest比较聚合收益 |
| base_latest | 同状态三次测量中的最后一次 | 基础Qwen3.5-4B，adapter禁用 | 与rule_latest比较选择器 |
| base_median | 同状态三次测量的逐坐标中位数 | 同一基础4B，adapter禁用 | 与base_latest比较聚合，与rule_median比较选择器 |

采用本地已验证4B推理栈，Flash教师角色保持不变；本轮不引入模型大小、微调或历史窗口差异。已有159/189适配器不激活、不更新。基础4B是本轮待评估选择器，不将它描述为Flash模型。

## 预算、分母与数据用途

24条件×4方法=96条方法轨迹、12种子组；每条最多3次物理尝试，成功即停。每条件先重新进行至多2次控制/初始干预执行；合格后四方法共享初始干预，再各最多2次。因此最多24×(2+4×2)=240次独立物理执行，不是96×3次全独立执行。

各方法在首次失败状态取得默认1次+额外2次观测；之后用新状态的默认单次观测，不跨状态复用。规则/模型获取的有效反馈在同聚合方式、同状态时相同。动作分叉后只保证噪声协议/随机流定义相同，不谎称后续物理状态与测量数值仍相同。

模型每次实际修正最多调用1次，不隐式重试、挑答案或规则兜底；最多24×2模型组×2次=96次新增任务模型调用。服务健康回放调用单独统计，不混入任务调用。两模型组生成参数相同：greedy、seed42、enable_thinking=false、max_new_tokens128；输入超限拒绝，不静默截断。

预先报告完整1/2/3次执行预算曲线，来源为同一最大3次轨迹截断；它们不是三个独立实验。逐预算报告成功/执行、跳过、初始失败恢复、方法尝试数、实际唯一物理执行数、额外观测费、模型调用/token/延迟、非法输出与服务错误。按种子组报告配对差异，不进行事后有利预算选择。

这24条件继续作为机制开发诊断，既有结果不能因重新执行而变成新独立样本。不训练、不导出监督标签、不读最终测试。后续正式验证需在协议稳定后另定新种子并冻结；本计划不预先承诺显著或普遍提升。

## 输入与候选公平性

先生成有效反馈，再由同一无历史candidate builder生成菜单。rule与base在相同状态、相同聚合方式下必须得到逐项相同菜单。latest与median的反馈不同，候选数值/ID/排序允许随之变化；这里估计的是整条聚合处理路径效果，不声称两种聚合的菜单相同。

模型只看到当前有效反馈、当前执行参数和候选列表，history=[]；不看到三次原始窗口、审计original/delta/outlier、物理成功真值、未来轨迹或旧测试结果。不提供预先选好的rule答案。候选facts只能由可见反馈重建。规则和模型均沿用理想错误类型与阶段，此限制在论文中明确披露。

如果未来希望测试“LLM自主融合三次观测”，必须另设实验：给模型可见窗口并设计公平菜单，不能悄悄混入本四组设计。当前四组不检验长历史推理能力。

## 代码与调度工作包

拟创建独立observation_model_control_v1，保持已冻结目录不变。

1. `protocol.py`/`freeze.py`：固定24条件、四方法、预算、模型/执行源hash与父manifest；身份核验同时比较旧规则首段，记录已有开发用途。
2. `observation.py`/`policy.py`：复用冻结sensor算法；实现四方法路由、仅有效反馈的提示、同聚合方式菜单一致性检查。旧exposure保留为兼容指标，新增“动作实际消费字段”独立统计，未知measured类型应显式报错。
3. `service.py`/`client.py`：独立服务目录和经检查未占用的端口；复用现有4B加载/禁用adapter验证与EOS判定，固定模型身份。非法响应保留原文，任务失败但不自动重试；基础设施故障停止批量，保留已计费尝试。
4. `worker.py`/`audit.py`：共享初态、每组独立后续执行、预算与物理判据核验；原始请求/响应及每步结果落盘。新规则轨迹与旧冻结轨迹逐步核对，出现变化先定位，不用新结果覆盖旧结果。
5. `report.py`：四组全预算曲线、六组方法配对及每种子结果，主要比较为同选择器的聚合差异、同聚合方式的选择器差异。所有交叉比较标清，候选合法率不替代物理成功率。
6. `controller.py`/Slurm脚本：1卡模型服务+最多3卡仿真；资源不足自然等待。控制器跟踪作业实际终态，批量完成后提交最终CPU审计；保存全部子作业ID。最终审计缺失/被取消必须报未验收，不伪报全完成；结束后仅停止本轮服务并释放资源。

## 验收与分阶段执行

- [ ] 单元/回归：同状态配对、跨状态禁止聚合、无审计字段泄漏、菜单相同、adapter禁用、EOS/非法输出、停止/跳过计费、预算前缀和共享执行去重。
- [ ] 冻结代码/协议/模型身份；本地与服务器hash一致，跨cwd身份核验通过。
- [ ] GPU服务回放：基础4B身份与已有合法请求回放一致；不得把适配器模型当基础模型。
- [ ] 冒烟：预定前两种子×两物体×四组=16方法轨迹；工程审计和真实记录篡改拒绝通过后放行，不以模型胜出为门槛。
- [ ] 批量：复用冒烟，补其余20条件，最终96方法轨迹；失败保留现场、不静默重跑。
- [ ] 最终审计：分母、源hash、物理判据、预算前缀、输入边界、异常与调度终态；输出全部失败和无收益结果。

结果解释：若base_median只与rule_median持平，结论仍是聚合模块有贡献，不能宣称模型比规则聪明；若模型显著失误，先查输入/候选与失败案例，不立即追加训练轮数。只有形成可追溯训练目标和冻结新评估设计后再讨论定向微调。
